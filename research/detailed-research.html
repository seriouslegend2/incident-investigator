Agent-contract research and reanalysis

Rechecked primary sources on 20 October 2026. This note records the reasoning behind the separate agent contracts, not new production results or a claim that another system uses our exact seven roles. D2 remains removed; D1 owns reasoning plus orchestration.

What changed after reanalysis

  1. Made D1's initial navigation/source access explicit: it is not blind, but does not have a hidden correct workflow.
  2. Defined one shared Task/Result protocol instead of seven incompatible envelopes. Per-agent documents specify extensions and actual examples.
  3. Added applicability checks for late parallel results; a global revision change alone is not sufficient to reject useful independent evidence.
  4. Bound final approval to exact report and dependency versions; material changes revoke affected approval, not automatically every approval on any case event.
  5. Defined deterministic investigation_incomplete delivery when valid final review is unavailable. This is distinct from a reviewed inconclusive diagnosis.
  6. Preserved code/data/AI discovery before implementation-specific questions, original-source review and explicit unknowns.
  7. Made the investigator's own failure modes testable: false premises, stale scope, summary drift, duplicate results, review outages and unsupported confidence.

Remaining implementation decisions

Choose actual adapters, authorization implementation, case-store transaction/version strategy, model/provider, prompt versions, typed schemas and numerical budgets through implementation/testing. Decide material-change heuristics and measure false-positive/false-negative review invalidation. Evaluate review granularity and caching under high-fanout incidents; do not claim free or perfect review. Add human evaluation for intended-behavior ambiguity and rare causal errors.

No agent or pipeline has been implemented, run against live systems or load-tested here. The documents are ready for contract-level discussion and implementation planning; tests in them are planned acceptance criteria.

Reading guides · agent-protocol.md

Shared agent protocol and lifecycle rules

Status: proposed implementation contract, researched and reviewed on 20 October 2026. No runtime, model prompts, source integrations or behavioral tests are implemented by these documents. The active agents are D1, D3, D4, D5, D6, D7 and D8; D2 is removed. Start with the agent guide.

For physical deployment, the LLM/tool execution loop, credentials and where code/replicas/logs live, read how the agents actually run. The tool catalog and JSON schemas/examples are the exact interface reference. Earlier conceptual payloads in historical architecture discussions are not additional APIs.

1. Stable roles, dynamic assignments

A role defines expertise and permitted capabilities, not a fixed task or mandatory execution order. Every invocation receives a bounded question, available knowledge, unknowns, output requirements and limits. Discovery tasks may lack service/time/version identifiers; they must record search assumptions, not invent those identifiers. Specialists reason locally and suggest follow-ups. Only D1 allocates cross-agent work; D7 can require missing evidence or reject a conclusion, but does not become a second orchestrator.

Production tools are read-only and tenant-scoped. Writing the investigator's own case records, task events and report drafts is allowed; that does not authorize production DB writes, message sends, deployments or arbitrary shell execution. Tool names in these contracts are proposed adapter interfaces, not installed integrations.

2. D1's bootstrap is explicit

At start D1 receives report_text, the configured role/tool registry, a trusted authorization context, source-directory access, an empty case/knowledge state and configured limits. It does not receive the correct service, incident time, workflow or cause.

D1 can use navigation tools: catalog.search, catalog.describe, history.search, case.read, targeted evidence.fetch, delegate_task and request_clarification. Tools enforce authorization outside model-controlled arguments. The directory contains searchable metadata, not guaranteed runtime truth. If it is missing/stale, perform bounded indexed discovery through an appropriate specialist or clarify scope; no unlimited organization-wide raw scan.

The four domain roles have deeper source adapters. Capabilities can overlap where justified; the role names are expertise boundaries, not isolated knowledge. D5 receives D4's discovered code-to-data ReadContract, cited code excerpts and unresolved bindings; it can fetch their originals. D4 can inspect relevant schema metadata. D5 can begin with source/schema discovery and request D4's verification when application usage is unknown. D7 has authorized original-evidence fetch and bounded verification queries so it is not restricted to D1's selected prose. D8 reads the selected case snapshot and cited originals, not unrestricted exploratory production searches.

Each Task contains these fields; example values are invented fixtures, not hidden input hints or tuned budgets. All object keys are required in the strict schema; unknown nullable values use null, collections use empty arrays. The model receives role instructions and permitted tool schemas separately. Credentials, trusted caller policy and executable tool code are not model inputs.

case_revision identifies the planning snapshot; it changes on accepted case updates. scope_revision changes when the investigated entity/cohort/environment/time interpretation changes materially. dependency_versions identifies the particular claims/assumptions the task relies on. Artifact/source versions and actual searched time ranges belong in the source/coverage records. These are different concepts; a DB query snapshot is not an incident-time historical snapshot.

Authorization is attached in a trusted context, not granted by model-written scope. inquiry_kind is discovery, hypothesis_test, verification, report_draft or report_review. Unknowns may be empty, but every specific premise needs a basis or explicit exploratory label. Search terms may be tentative; invented resource IDs cannot be treated as discovered targets.

4. Model answer versus trusted result envelope

The runner repeatedly calls the LLM, executes validated requested tools and returns their bounded receipts. The model's final structured object is AgentAnswer-v1; it does not mint source evidence, runtime identity, hashes or measured costs:

FieldRequired meaning
agent_idMust equal the role requested by the runtime; not permission to switch roles.
execution_statuscomplete, partial, failed or cancelled; complete means the assigned query/task finished, not that a cause was proved.
observationsScoped source-backed observations, each with evidence references; interpretations stay separate.

Runtime constructs Result-v1: protocol_version, result_id, case_id, task_id, attempt_id, agent_id, case_revision, scope_revision, dependency_versions, answer_state, the validated answer, tool_receipt_refs, actual errors, and measured cost (elapsed/tool/model calls, nullable token and backend scan counts). answer_state=valid requires an answer; unavailable, invalid or cancelled uses answer=null. It validates identities/references before applicability checks. Exhausted model/schema-repair attempts preserve actual receipts and errors; no fabricated model answer or review acceptance is required for deterministic incomplete delivery.

Adapters register original evidence independently of agent prose. Observation/interpretation IDs inside a model answer are task-local labels; runtime assigns registered versioned claim/artifact IDs. Returned citations are checked against the source store and authorization. A real source ID can still be irrelevant; structural validation does not establish semantic support.

delegate_task is an idempotent D1-only control tool: validates a proposal, clamps/reserves budget and schedules once. Runtime fills task/attempt IDs and revisions. D1's lead_decision.dispatched_task_refs records those already-created tasks; its final answer must not enqueue them a second time. Specialists and D7 only suggest cross-agent follow-ups. Read-only production tools do not prevent investigator-owned task/artifact writes.

report.store_draft validates D8's structured content and freezes the artifact, hash and dependency manifest. D8 echoes returned identities; it cannot self-approve or invent a successful store. D7 receives that exact artifact and target manifest for report review. See schemas and runtime-only checks.

5. Rule A: late parallel results do not blindly update current state

  1. Receive an event identified by case_id, task_id, attempt_id and a unique result ID. Deduplicate ingestion; repeated delivery does not count as independent evidence or execute side effects twice.
  2. Preserve authorized source evidence and the original result with its scope/dependency metadata. Do not overwrite current claims directly from a worker response.
  3. Compare the task's scope/dependency versions with current state. A changed global case revision alone does not invalidate an independent result.
  4. If the same question still applies and its dependencies/source bindings remain valid, atomically apply the result against current versions. If relevant scope/dependencies changed, mark needs_revalidation. D1 assesses applicability; required new premises still go through D7. Old-scope observations can remain useful history/counterevidence, but cannot silently become facts about the new scope.
  5. Unauthorized/malformed results are rejected; obsolete results can be archived. Acceptance states are applied, needs_revalidation, archived or rejected, assigned by case-ingestion policy, not by the producing agent.

Example: D5 checks group A under scope revision 2. D1 changes the investigation to group B at revision 3. A's result arrives late: retain it as A-scoped history; do not use it to explain B. A separate result about unchanged worker code may still be reusable after applicability checks.

Use a transactional/version-checked state update and an append-only event/audit history; no particular database is selected. Cancellation is best-effort: even a cancelled task may return late. Shared limits still charge work already spent. Agents propose records; they cannot rewrite historical evidence, their own acceptance status or review approval.

6. Rule B: review approval is version-bound and revocable

A claim review targets claim revisions, scope and a dependency manifest of source references/versions, related claims, coverage and relevant missing/contradicting evidence. D7 verdicts are accept, revise, insufficient or failed. Acceptance is scoped support, not proof of universal truth.

A final report review also binds the exact report bytes/hash and report version, diagnosis status, scope revision and dependency manifest. Report hashes bind artifacts; they do not prove claims are true. Normal formatting/encoding is finalized before review. D1 may add transport metadata outside the artifact but may not paraphrase the approved report.

Materially changed scope, changed supporting premises, new relevant contradictory evidence, withdrawn support, changed limitations/actions or changed report bytes invalidate affected approval. Unrelated evidence or an independent task event need not trigger a complete re-review. Track dependencies; batch related new-premise reviews and reuse only matching valid reviews to keep cost bounded.

Before delivery, an atomic guard checks artifact identity, approval validity and whether an unresolved material-change flag affects the reviewed claims. If stale, pause delivery and re-review/rewrite within budget. Policy can enforce declared bindings/flags, not perfectly determine semantic materiality; uncertain relevant changes conservatively reopen review. A post-delivery contradiction creates a superseding report/correction record, never a silent rewrite of history.

7. Rule C: explicit ending and reviewer-failure behavior

Keep diagnosis status distinct from execution/review status:

OutcomeMeaning and delivery rule
reviewed_report + cause_supportedA specific cause/contributors are supported for stated scope; D7 accepted the exact artifact and dependencies remain valid.
reviewed_report + cause_unresolvedSymptom is established but causal evidence is insufficient; D7 can accept an honestly inconclusive report.
reviewed_report + complaint_unverifiedAvailable searches could not establish a matching issue; does not mean the system is healthy. D7 accepted the limitations.
investigation_incompleteNo currently valid final approval: reviewer unavailable, budget exhausted, orchestration failure or unfinished required checks. Return deterministic status, stop reason, pending work and clearly unreviewed finding references—not an approved causal narrative.

Reserve configured budget for writing/review but do not promise it is always sufficient. All retries/rework count against global limits. Failed or absent review is never accept. A model is not required to generate the fallback status. If an earlier approval is still valid for the exact current scoped artifact, delivery can use it; otherwise incomplete is safer than pretending review succeeded.

Within budget, D1 can change source/query/scope, retry transient failures or ask clarification. It cannot retry until a critic agrees. Persist a checkpoint and stop reason. Explicit human/user resumption can create new tasks from the checkpoint; do not run an unbounded background investigation after reporting completion.

8. Self-audit and security

Use the question-grounding contract: distinguish known premises, exploration and unknowns, and make task origins visible. Review new read/architecture premises before they constrain cross-domain work, flagged contradictions/prerequisite gaps, causal promotion and final delivery. D7 may batch related checks; neutral discovery can continue while uncertain premises stay unverified.

Enforce read-only source capabilities, tenant filtering, resource limits, privacy/secret redaction and tool parameter validation outside the model. Source documents, logs, prompts and code comments are untrusted evidence, never instructions to broaden permissions or call arbitrary tools. Shared caches include trusted authorization and source/time/version identity and invalidate on relevant changes.

9. Planned integration tests

These are acceptance criteria, not executed behavioral tests:

  • Late result for group A cannot explain new group B; unchanged independent code results are not needlessly discarded.
  • Two result handlers cannot overwrite one another's accepted revisions; duplicate events do not duplicate facts, delivery or cost accounting.
  • A draft approved before contradictory evidence cannot pass the delivery guard. Unrelated evidence does not automatically revoke all reviews.
  • Editing approved report bytes, scope, recommendations or supporting claims requires valid updated review; delivered reports remain immutable history.
  • D7 timeout, malformed verdict, denied source or exhausted budget cannot become approval. The incomplete status works even if D1/D8 fails.
  • Partial source reads do not become absence claims; relevant late data reopens affected conclusions.
  • Invented components/irrelevant citations/omitted prerequisites are challenged; measure review escape rates rather than assume perfect detection.
  • Independent tasks really overlap; dependent tasks wait for prerequisites. Every role/attempt consumes the same global budget.
  • Baseline receives the same tools, permission scope, evidence availability and failure replay; report all model/review costs.

The lifecycle fields and policies above are our proposal. Anthropic documents scoped delegation and asynchronous coordination challenges; incident.io documents findings that can be overturned; Resolve documents independent verification. PostgreSQL documents concurrency/snapshot behavior, not our report-approval protocol. See research and reanalysis for primary links, distinctions and unresolved implementation choices.

  • Maintain shared investigation state and task dependencies.
  • Gather additional evidence through feedback loops.
  • Bound retries and execution, and define termination conditions.
  • Recover from failures of agents or tools.

Final reports must contain ranked hypotheses, supporting evidence, contradicting evidence, confidence levels, and recommended actions. Facts must be distinguished from assumptions. An inconclusive result must be possible when evidence does not justify a conclusion.

Confidence scores reported by products are not automatically calibrated probabilities. A source that merely promises an accurate RCA does not establish contradiction handling or abstention.

Research checked: 2026-10-20. This note concerns evaluation design, not an implementation plan or selected architecture. The assignment remains the controlling specification: at least ten test incidents, misleading/conflicting evidence and tool failures, and a single-agent baseline using the same tools.

AIOpsLab: environment and evaluation harness

Microsoft's MIT-licensed project deploys applications, injects faults, drives workloads and exposes telemetry to agents. Problems bind an application, task, fault, workload and evaluator; tasks cover detection, localization, analysis and mitigation. The published MLSys 2025 evaluation selects 48 problems, so “48” describes that evaluation rather than every current repository problem. Repository, primary paper

The checked quantitative evaluator counts assistant trace entries as steps and estimates tokens using a fixed tokenizer over trace content. Such estimates need not equal billable model usage, particularly when internal agents, retries or repeated prompt history are absent from the trace. Quantitative evaluator

Its qualitative evaluator uses an LLM judge over formatted traces, with a 1–10 reasoning score. This is a distinct kind of evidence from deterministic root-cause matching. Qualitative evaluator

ITBench: scenario success and snapshot replay

The 2025 paper reports a low SRE scenario-resolution rate of 13.8% for its evaluated agents. A newer repository describes snapshot-based diagnosis using ITBench-Lite, a runner, MCP tools and an evaluator producing separate JSON outputs. Read these as different benchmark versions. Original paper, replacement agent framework

For a later assignment experiment, fixed telemetry snapshots offer a useful idea: both approaches can receive identical evidence and failure schedules. This does not require adopting the ITBench stack or executing remediation.

RCAEval: offline telemetry and ranked localization

The RCAEval publication provides nine telemetry datasets with 735 failure cases and 15 reproducible baselines. These cover metric-, trace- and multi-source analysis. The current repository has evolved beyond that publication, so pin a version when reproducing results. Publication, repository

The checked repository exposes root-cause labels and ranked evaluation, and its license section distinguishes authors' MIT-licensed code/data from bundled baselines with different or missing licenses. Do not assume one repository-level badge licenses every dependency. Licensing and changelog

This can inspire realistic telemetry shapes and deterministic labels. It cannot replace the assignment's deliberately contradictory observations and tool-failure tests without an explicit adaptation.

Implementation plan — incident investigation system

Decision: implement one durable investigation control plane with seven logical LLM roles and a separate policy-enforcing tool gateway. It is not seven VMs, an all-access process, or an LLM with database/cloud credentials. The model chooses a permitted next operation; trusted backend code validates and performs it.

This is a build plan, not a claim that the integrations, replica, indexes, IAM identities or benchmark already exist. It is based on a read-only review of the KookarCore checkout named by the team. Source facts and recommendations are labelled below.

Implementation decision record (updated)

The implementation is a real demo application, not a fixture-only workflow visualisation:

  • Each of D1, D3, D4, D5, D6, D7 and D8 gets its own KookarCore-style package: prompt seed, Pydantic request/result contracts, restricted tool wrapper(s), executor/build definition and tests. D2 remains absent.
  • The LangGraph workflow calls actual OpenAI model turns with structured tool calls. It must not encode a fixture's final diagnosis in code or let the model simply repeat one.
  • Demo evidence is seeded but real: sample logs/traces, deployment/config records, code-index records, database/history records and AI-run records. Tools query those sources and return bounded, cited evidence.
  • Postgres/Supabase persists cases, task invocations, tool calls, evidence receipts, claims and report revisions. LangSmith receives actual LLM/tool execution traces correlated by case and task identifiers.
  • API keys and connection strings are runtime configuration only. They are never committed, embedded in prompts or placed in documentation.
  • The initial demo does not connect to live AWS/Azure/GCP or production databases. A later live connector follows the gateway/source-catalogue design in this plan; it is not simulated by broad credentials.

The previous fixture-only prototype is intentionally discarded before this implementation starts.

1. What we are building

An operator supplies a vague complaint such as “customers in group A did not get a message.” The system will:

  1. Create a durable case, preserve the original wording, scope and clock.
  2. Discover candidate services and expected workflow boundaries rather than assuming a table, repository or log group.
  3. Request only the specialist checks needed to locate the first unexplained boundary.
  4. Store every query result as cited, bounded evidence with source/revision/time/coverage.
  5. Compare expected implementation with observed execution and data/AI behavior.
  6. Return a reviewed incident report: observed flow, expected flow, supported cause or unresolved alternatives, counterevidence, affected scope, gaps and proposed (never automatic) next actions.

The seven logical roles are D1, D3, D4, D5, D6, D7 and D8. There is deliberately no D2. D1 owns reasoning and dynamic orchestration; D7 is an independent evidence critic. This is our design choice, not a claim that the assignment’s example agent list must be copied.

Important limits — source facts

  • The current KookarCore/Supabase client is application-capable: generic helpers and service-role configuration exist. It must not be reused as D5’s investigator credential.
  • Existing queue run bookkeeping is explicitly best-effort. It cannot be the authoritative incident/evidence store.
  • Existing EDA2 deduplication, scope tokens and workflow/callback state have finite TTLs. They cannot be the long-lived investigation authority, and a failed callback must be recoverable rather than merely retried.
  • Current Workers can safely run the LLM loop, but a Worker should not be granted direct unrestricted access to private databases, cloud accounts or secrets.
  • Checked-in prompts can be seed/fallbacks while remote prompt management is runtime truth. Investigation must record the exact prompt/model configuration actually observed, not infer it from a repository file.

Control plane: an operator-facing, authenticated API, scheduler, case store and delivery guard. It may be implemented beside KookarCore’s EDA2 workflow engine. Choose its ingress explicitly; the inspected Core ACA deployment is internal/private, not evidence that this API should be public.

LLM runner: one logical worker/runtime can host all seven roles. Kookar’s Cloudflare Worker factory/queue approach is a good fit for asynchronous task execution. It must receive task inputs, allowed tool schemas and redacted tool results—not credentials or network-wide access. Deploy it as a dedicated incident Worker service with its own minimal secret bundle, queue/DLQ and service identities. Putting incident agent folders into the existing Worker bundle does not create per-agent secret isolation.

Private evidence gateway: a new small service in the organisation’s private network/VPC/VNet (for example, ECS/Fargate, EKS, VM or equivalent). It contains cloud SDK/API clients, Git host client, replica connection pools, connector policies and audit logging. It is the only component that can reach private sources.

Runner-to-gateway bridge is a required deployment decision, not an arrow in the diagram. Either run the role runner inside the same private network, or publish the gateway only through an authenticated private ingress/Tunnel/Access route. For the latter, require both an edge service-token check and a separate application-level audience/scope token (plus mTLS where feasible), an egress allowlist, and source-target allowlisting. Test the positive path and denial for unauthenticated/wrong-identity callers. Never expose the replica or cloud control plane directly to a public Worker.

Storage: use a durable transactional database/object store for cases, receipts and immutable reports. Do not rely only on Redis, an LLM trace product or a queue cache. Encrypt it, apply retention and use object storage for large redacted evidence pages.

5.2 Code and deployment index

  1. Install a read-only GitHub App (or equivalent) scoped to approved repositories.
  2. Build an async repository synchroniser: webhook/poll → immutable commit fetch → parser/symbol/reference index → service/deploy binding extraction.
  3. Keep an exact-revision content store or on-demand bounded fetch service. For billion-line estates, index first; only read a cited file range after search narrows it.
  4. Ingest CI/CD and deployment provenance: artifact/image digest, manifest revision, rollout time, environment/region/instance labels.
  5. Publish index freshness, unindexed repositories/languages and missing deployment mappings as visible coverage gaps.

5.3 Read-replica data connector

Create IncidentReadRepository, entirely separate from KookarCore’s generic write-capable Supabase client:

  1. Provision a dedicated database login with TLS, CONNECT, USAGE and SELECT only on approved views/tables; no ownership, BYPASSRLS, DML, DDL, temp-object/large-object privilege, callable functions/RPC or primary endpoint. Revoke EXECUTE from PUBLIC and the investigator role for non-approved functions, and set/verify default privileges for future functions.
  2. Use curated incident views where raw data has sensitive message/user payloads. At case creation, map the authenticated operator to an immutable authorised source scope. Gateway maps that scope to each source’s actual tenant/house/composite predicate; an unresolved mapping fails closed. Agent tool arguments never choose another tenant.
  3. Network-restrict the connector to the replica endpoint and prevent primary DNS/credential fallback. Start every request in a read-only transaction; set statement, lock, result, scan and page limits; use parameterized templates only.
  4. Put a query policy compiler before the driver. It validates a named template and typed filter fields, injects the case-authorised source scope and environment predicates, and rejects broad/paged-out/unsafe requests.
  5. Capture connector receipt fields: connection ID (not DSN), replica observation time/lag, template version, relation, allowed columns, row count, continuation state, redaction summary and error class.
  6. Use a separate audit/history connector for incident-time state. Define its event-time semantics, retention window, ordering/lag, delete/tombstone treatment and snapshot completeness. Only a source that documents coverage for the claimed interval can support an historic claim; a current replica cannot answer “what was the value last Tuesday?” by itself.

KookarCore’s local migrations show broad service-role access in parts of the current application. Verify deployed grants/RLS with the database owner; the plan must not assume that source policies are suitable for an investigator.

5.4 Cloud, logs, deploy and configuration connectors

  1. Create a read-only workload identity per provider/source group. Grant only the named resource paths needed by registered adapters.
  2. Build bounded query templates for logs/traces/metrics: target service, environment, interval, correlation keys, limit and paging. Record query timeout, retention/sampling and searched interval.
  3. Build deployment provenance queries: service instance → deployment ID → artifact digest/build → revision/config manifest. A code commit is evidence only after this binding.
  4. Expose configuration as effective nonsecret metadata: name, source, version/hash, last change, scope and presence. Redact values and tell the report when a secret/effective value was intentionally inaccessible.
  5. Validate any webhook/deploy event at ingestion; it updates a catalogue lead, not a causal conclusion.

5.5 AI application connector

For each AI workflow register model provider, trace project, prompt registry, retrieval indexes/vector stores, tool audit store, handoff/state store and retention policy. The D6 adapter reads:

  • exact run/trace and timing;
  • rendered prompt or versioned prompt reference;
  • model/provider/settings actually recorded;
  • retrieval query, document IDs/scores/filter and returned context;
  • tool calls/results and parent/child handoffs;
  • state/checkpoint versions and failures.

Prompt/model/retrieval evidence can be sensitive. Redact/minimise before returning to a role runner and retain access decisions in receipts.

8. End-to-end execution

  1. Create case. API validates operator identity/scope and stores raw complaint. It binds the operator-authorised source scope immutably to the case/scope revision. Runtime assigns case ID and records its current clock. No source access is assumed.
  2. Discover. D1 calls catalogue/history discovery. It creates a workflow boundary map such as intent → record → enqueue → consumer → destination resolution → provider accept → callback/delivery → customer-visible.
  3. Locate the first unexplained boundary. D1 invokes only relevant specialists. Example: D3 for observed attempts; D4 for code/deployed revision; D6 when an AI handoff is involved. Independent checks may run in parallel only when they share no prerequisite.
  4. Gather safely. A role requests a declared tool. Broker validates task/role/schema/scope; gateway resolves the opaque configured source ID, applies access/redaction/bounds, runs the query and persists receipt/evidence. The model gets a small result page plus cited IDs.
  5. Compare explanations. D1 maintains alternatives and asks a discriminating question before causal promotion. Example: “queue stalled” and “recipient data missing” predict different execution/data observations.
  6. Cross-domain binding. D4 verifies code/deploy/config; D5 checks the cited data path; D3/D6 establish observed behavior. Time, tenant, environment, region and deployed version must match.
  7. Review and write. D8 drafts only from stored claims. D7 independently checks exact cited originals, alternatives, contradictions, scope and unsupported certainty. A D7 failure or budget exhaustion yields investigation_incomplete, not approval.
  8. Deliver safely. Delivery guard hashes the exact report and dependencies again. If relevant evidence or draft changed, return to D1/D7; do not silently send stale text. The report proposes actions; it never runs remediation.

Concrete message failure example

Complaint: “Customer group A did not receive the reminder.”

  1. D1 catalogue search finds a messaging service and uses D3 to search a bounded recent interval. D3 returns a cited attempt ID and finds a destination-resolution error before provider submission.
  2. D1 asks D4 to locate the deployed resolver. D4 binds the running deployment to an artifact/commit, reads the resolver path and returns ReadContract RC-17: a lookup of group destination fields, plus uncertainty about the environment connection mapping.
  3. D7 checks that RC-17 actually cites the deployed revision and says whether its premises are sufficient.
  4. D1 asks D5 with RC-17, group A and time. D5 verifies schema/replica binding and returns: the required destination row was absent at the current replica state; historic state is unavailable. This is not yet proof it was absent at incident time.
  5. D1 requests an audit-history check or states the temporal gap. If history shows deletion before the event and D3 shows resolution failure, the report can support the missing-data cause. If history is missing, report a supported current inconsistency plus unresolved incident-time state, not a definitive root cause.

9. Security, privacy and safety gates

  • Separate identities for API, dedicated incident Worker, incident queue/DLQ, gateway, each cloud adapter and each replica. Prefer short-lived workload identity and mTLS/OIDC service-to-service authentication.
  • Broker enforces role/tool/source/tenant/environment policy on every call; trusted case scope is injected and verified against the operator authorisation. LLM-provided arguments never widen permissions or select a tenant.
  • No generic shell, arbitrary URL fetch, arbitrary SQL, raw secret/config-value tool, deployment mutation, replay, message send or automatic remediation tool.
  • Redact/minimise PII and secrets before model context; mark withheld fields/coverage. Treat repository text, logs and retrieved data as untrusted evidence, never tool instructions.
  • Encrypt data in transit/at rest; define regional/data residency, retention, deletion/legal-hold and access-review policies with security/legal owners.
  • Audit operator, runtime, connector and delivery actions. Store query shape/receipt, not credentials or raw sensitive bind values. Treat database audit rows as application append-only records unless access/recovery policy plus WORM/hash anchoring has been operationally proven.
  • Rate/row/scan/token/concurrency budgets apply at gateway and scheduler. Source error, empty response, sampling/retention gap, denial, timeout and model/schema error remain different states.

Reading guides · question-grounding.md

How the investigator earns its questions

Current architecture: D1 owns reasoning and orchestration; D3–D6 are domain investigators; D7 independently challenges the investigation; D8 writes the report. There is no D2. This is a design contract and acceptance-test plan, not implemented or proven hallucination prevention. See the short HTML explanation.

1. Correct the earlier mistake

The earlier walkthrough asked whether a worker read the wrong database field or used stale cache data before showing how the investigator learned that lookup's implementation. That skipped a necessary discovery step. A plausible engineering explanation is not evidence that a particular component, field or path exists in this application.

The system must distinguish four categories:

CategoryMeaningPermitted use
Observation / implementation findingSource-backed fact with scope, time/version and coverage. Review may still dispute its interpretation.Establish the current working map and premises of a specific question.
General investigation methodDomain-independent strategy, such as locating the failed stage, tracing inputs or comparing available successful attempts.Ask open discovery questions without pretending the architecture is already known.
Exploratory hypothesisA possibility based on general expertise or a partial clue, explicitly not established.Ask a neutral discovery/test question. It must not become an asserted component, tool parameter or factual conclusion.
Unknown / missing prerequisiteAn uninspected dependency, field, deployment binding, history or intended outcome.Delegate discovery, clarify scope or report the gap. Do not fill it with a plausible story.

General expertise may suggest “a cache could be involved”; the valid question is “Does this read path include a cache?” until that connection is established. “Why did cache C7 return stale data?” presupposes both its existence and failure; neither may be silently invented. Search keywords are leads, not registered entity identities.

2. How questions become specific

  1. D1 starts with the complaint plus configured source/tool capabilities. It does not receive hidden service/time hints or an internal route.
  2. D1 asks a general question: “Find candidate failing attempts and the stage/outcome recorded.” D3 searches bounded sources and reports both findings and scope uncertainty.
  3. If the stage is recipient resolution, D1 asks D4: “Explain this stage in the relevant implementation: inputs, dependency reads, decision branches, error conditions and deployed-version confidence.” It does not name a database field before discovering it.
  4. D4 returns source-linked behavior and suggested follow-ups. For example, the lookup reads legacy_destination_id from a particular mapping source and aborts on an empty value. That information enables a specific D5 query. If the deployment binding is unverified, label the code finding provisional and verify it before incident attribution.
  5. D5 inspects the established source/read scope and discovers current/historical data, including alternate fields where supported by the schema. Only then does a concrete code/data compatibility hypothesis become grounded.
  6. D1 combines findings, checks which premises are still unverified, and delegates a distinguishing test. D7 independently challenges the claim and the question's premises using original sources and query coverage. The sequence can revisit discovery; it is not a mandatory fixed pipeline.

An agent result contains observations, implementation_behavior, source references, coverage, interpretations, unknowns and suggested follow-ups. Keep interpretations separate from source observations. Specialists can suggest questions D1 would not know to ask; D1 need not read the whole codebase to use their evidence.

3. The task contract: record why this question exists

Each task/decision records:

  • inquiry_kind: discovery, hypothesis test, evidence verification, report draft or report review, using the identifiers in the shared protocol.
  • question: phrased without presenting unverified details as facts.
  • known_premises: claim/source references establishing the relevant entities and observed/implemented behavior.
  • exploratory_assumptions: possibilities not yet established, with their rationale and status; an empty list is valid.
  • unknowns: missing behavior, source identity, scope, version, historical state or expected outcome.
  • why_now: what finding, contradiction, coverage gap or general investigation goal motivated the task.
  • expected_information: what observations could distinguish alternatives; a discovery task may simply seek a source-backed next boundary.
  • Trusted authorization scope, current candidate scope, query/scan/context budget and prerequisite/task references.

Do not fabricate source references to satisfy this structure. A valid reference does not by itself establish that the cited source supports the premise.

4. Check the investigation itself

Before dispatch

Ordinary validation checks structure, existing references, entity identifiers, scope/permissions, prerequisite status and limits. A query cannot target a fabricated concrete resource as if it had been discovered. Discovery searches may use tentative names/terms, clearly typed as search candidates rather than facts.

D1 records a short decision justification and self-check: What is known? Which premise is still an assumption? Is this the relevant deployed implementation/read scope? Which observation could contradict the current explanation? Is a required prerequisite missing? These are observable decision records, not private chain-of-thought.

Code cannot reliably prove semantic grounding or notice every omitted question. D7 receives suspicious premise introductions, contradictions and causal claims with original-source access; it checks relevance, version, meaning and coverage independently. It can return a concrete discovery request, not only polished wording. This is a bounded review role, not a permanent monitor on every specialist.

Review must not depend entirely on D1 noticing its own mistake. A non-LLM policy gate enforces review at declared points: first use of a new source-derived architecture/read-contract premise to constrain cross-domain work, a flagged contradiction/missing prerequisite, causal promotion and final delivery. D7 can batch related premises. Neutral discovery can continue with unknowns; unsupported premises cannot silently become accepted facts because the review failed, timed out or exceeded budget. The gate can enforce that review occurred, not that D7 judged correctly. This adds cost and may delay investigation; include it in evaluation rather than claiming perfect detection.

During investigation and before closure

Maintain a dynamic coverage frontier: each discovered execution boundary has supporting evidence, a failed observation or an explicit unknown. Each causal explanation has supporting/contradicting sources and missing links. D1 and D7 check the claim-specific missing links, not a universal requirement to inspect every domain.

If a conclusion requires historical database values, the current row is not sufficient. If it requires attributing a code revision, bind that revision to the affected execution. If a prompt is blamed, inspect the rendered prompt/context actually used, not just the latest template. If an expected path comes only from faulty implementation, seek a contract/test or retain uncertainty about intended behavior.

When D7 finds a gap, invalidate or downgrade dependent claims as appropriate, assign bounded follow-up or deliver an inconclusive/limited report. Do not repeat queries until the critic agrees. If scope changes or late evidence contradicts a premise, reopen affected claims and obsolete tasks. If no new information arrives, broaden a justified source/branch, ask a targeted clarification, or stop with the unresolved frontier.

An inconclusive/limited final report still requires valid review of its exact artifact. If review is unavailable or no valid approval remains at the stop boundary, return deterministic investigation_incomplete status instead of presenting an unreviewed causal narrative. Late-task applicability, material-change invalidation and delivery rules are defined once in the shared protocol.

Do not rely on the user to discover omitted prerequisite checks. Nonetheless no finite checklist or critic guarantees zero hallucinations or complete coverage; measure unsupported-premise escape rates and appropriate abstention.

6. Acceptance tests the implementation must include

These are planned tests; none is claimed executed here.

  1. Invented component: D1 proposes “stale Redis” with no Redis evidence. It must remain an exploratory possibility; reject a concrete fictitious resource ID or reframe as bounded discovery. It cannot enter the final report as fact.
  2. Unknown implementation: give only recipient_missing; the next action must learn relevant behavior or explicitly explore possibilities, not assert a field name or storage topology.
  3. Wrong cited support: a real source ID points to an unrelated function or tenant. Structural reference validation may pass; semantic review must challenge it. Measure the escape rate rather than assuming success.
  4. Missing prerequisite: current DB row exists but incident-time history is unavailable. D7 requests the missing check; report the gap if it cannot be obtained rather than inventing migration timing.
  5. Stale code/prompt: relevant latest-branch content differs from the actual deployed revision/rendered generation. Preserve the binding gap or fetch the correct artifact; do not silently substitute it.
  6. Surprising specialist lead: D4 finds a dynamically selected dependency not present in the catalog. D1 can expand through that sourced edge instead of forcing the initial map.
  7. Contradiction / ignored alternative: a successful or affected cohort conflicts with the leading story. D7 can request the original evidence and a rival test, and D1 revises or narrows the conclusion.
  8. Repeated unproductive checks: identical complete stateless queries or repeated review requests produce no information. Bound retries and switch strategy/clarify/stop rather than loop.
  9. Summary drift: a partial query becomes “no record exists” in a specialist summary. Validation/review must retain the original partial status and prevent factual promotion without sufficient support.
  10. No diagnosis possible: missing code, history and correlations leave the path unknown. Return unverified/inconclusive scope; do not manufacture an end-to-end explanation.

Measure question specificity versus available knowledge, fabricated-entity/premise rate, missed-prerequisite rate, critic detection and escape rates, recovery from challenges, extra calls/latency/tokens and inappropriate certainty. Test these beside root-cause accuracy and source-retrieval recall. The equal-tools single-agent baseline gets the same evidence and limits; the critic is part of measured system cost.

6. Replica policy and temporal correctness

Record queries use approved replicas with a dedicated least-privilege identity. Do not reuse the application's privileged service key. Connector-side relation/column/tenant rules, safe query compilation, timeout/scan/result caps and read-only transactions are required. No arbitrary SQL/RPC/function execution; allowlisted templates must themselves be reviewed for side effects. Metadata/diagnostics that a replica cannot provide remain gaps or use a separately authorized read-only monitoring API—never an automatic primary fallback.

data.read_bounded reads current state. data.history uses an actual configured audit/change-history source; a timestamp argument cannot make an ordinary replica a historical database. Return observation time, available replay watermark/lag and unknown freshness. A missing replica row is not alone proof that the application saw missing data. An inaccessible table, empty result, partial query, missing history and schema mismatch are distinct outcomes.

8. Failures, budgets and what is not claimed

The runtime caps both backend work and response size, counts all model/tool/review attempts, and cancels bounded work when limits expire. Read-only queries can still be expensive. Source evidence stays versioned; approved reports are immutable and checked again at delivery. See the shared lifecycle rules.

Large-estate investigation design

1. The architectural change

Separate estate preparation and indexed retrieval from per-incident agent investigation. The model never receives the whole estate. Existing agents investigate bounded questions using searchable source systems; they expand their scope when evidence warrants it. Adding context length or one agent per repository does not solve retrieval.

There are three logically different maps:

  • Estate map: discoverable services, repositories, deployments, APIs, queues, databases and AI workflows. Prepared continuously, incomplete and potentially stale.
  • Incident working map: only the relevant candidate entities/connections, with evidence and unknowns. Built and revised during investigation.
  • Causal explanation: which faults explain observed divergence. Neither dependency adjacency nor search relevance establishes causation.

No graph database, vendor or framework is selected. Typed adjacency records and existing search backends may suffice initially. A static code-call index alone cannot establish runtime HTTP/queue routing, configuration-dependent behavior or product intent.

4. Follow only relevant cross-repository boundaries

For a messaging complaint, an illustrative discovered path is:

6. Agent responsibilities at scale

No new permanent agent is needed for each service or index.

  • D1: reasoning plus orchestration: maintains competing explanations, combines cross-source findings, chooses distinguishing tests, owns scope/frontier, selected tasks, priorities, progress and stopping. Holds compact state and source references, not all raw evidence or every specialist conversation. The separate analyst is removed; D2 is a retired ID, not an available agent.
  • D3–D6: bounded local investigation; choose relevant queries, inspect originals, produce observations/counterevidence/gaps and flag unexpected leads. Several task invocations can pursue independent branches, within a shared cap—not an unbounded swarm per service.
  • D7: challenge the leading causal mechanism and ignored scope, with authorized access to source originals and ability to request a rival test outside D1's chosen branch. Separate context does not guarantee different model bias.
  • D8: write from scoped reviewed claims, including expected/observed path, failure point, supported causes/contributors, alternatives, actions and gaps. Every material claim references evidence, not merely another agent's prose.

The case file holds versioned findings, evidence references, query results/statuses, frontier/visited entities, task dependencies and budgets. Keep evidence snapshots immutable where retained; allow interpretations to be superseded and reconsider dependent conclusions. Source originals are fetched on demand. Context compression retains contradictions, scope and unknowns; a summary never upgrades an uncertain observation to fact.

All seven individual contracts share the agent protocol. Late results carry scope/dependency versions and undergo applicability checks before atomic state updates; do not discard useful independent evidence merely because the global case revision changed. Duplicate deliveries are idempotently ingested. Final approval binds report bytes and relevant dependency versions, is invalidated by material changes, and is checked again at delivery. A reviewer outage or exhausted budget without valid approval yields deterministic investigation_incomplete status, not an unreviewed causal narrative. A reviewed inconclusive report is a different, valid outcome.

Find the first localized, verified divergence, or identify an evidence gap—not necessarily the earliest fault in the whole system. Failure localization is not causal attribution. Test explanations such as missing data, a wrong deployed lookup, stale configuration or an upstream handoff defect. Compare affected and healthy attempts/cohorts when available, explicitly noting differences in tenant, payload, load, time, schema and version. Temporal proximity or one good/bad comparison alone does not prove causation.

Missing spans/records, query truncation or retention gaps do not establish nonexecution. Preserve explicit empty, partial, timeout, denied and failed statuses. A stopped attempt does not establish that all retries or all customer groups failed.

Ground questions and audit the investigator itself

The question-grounding contract corrects a prior walkthrough that suggested wrong-field/cache questions before establishing the implementation. D1 starts with general investigation methods, not hidden application knowledge. Specialists explain relevant source-backed inputs, dependencies, decision branches and failure conditions; D1 then uses those findings and their suggested follow-ups to ask specific questions. Discover the actual read source/contract before targeting its fields or data. Generic hypothesis exploration is allowed, but does not establish that an application component exists or failed.

Each decision/task separates known_premises with source/claim references, exploratory_assumptions, unknowns, inquiry_kind, why_now and expected_information, plus scope/prerequisites/budget. “Does a cache exist in this path?” is an exploratory discovery question; “Why did cache C7 return stale data?” is unsupported if that resource/failure has not been established. Concrete query IDs and evidence references must be real, while tentative search terms remain explicitly tentative. Never fabricate a reference to satisfy the schema.

D1 records a compact self-check before choosing follow-ups: what is known versus assumed, whether scope/version/read semantics are established, what could contradict the explanation, and which prerequisite remains missing. These are public decision justifications, not private chain-of-thought. Code validation checks structure, reference/ID existence, prerequisite status, authorization and limits; it cannot prove that a source semantically supports a claim or detect every missing question.

D7 independently checks suspicious premises, contradictions and causal/report claims using original sources and the dynamic coverage frontier. The frontier records discovered boundaries, supporting evidence, failures and unknowns; it is not a checklist requiring all domains on every incident. Necessary code/deployment bindings, incident-time data or actual rendered AI context must be inspected or remain gaps before making claims that depend on them. If a premise fails, invalidate/downgrade dependent claims and direct bounded discovery/follow-up, or deliver an inconclusive result. The user should not be the mechanism that detects these omissions.

Declared review gates are enforced outside D1's discretion: a newly introduced source-derived architecture/read-contract premise used to constrain cross-domain work; flagged contradictions/missing prerequisites; causal promotion; and final delivery. D7 may batch related claims, within shared budgets. A failed/unavailable review leaves its claim unverified; nonpresupposing discovery may continue, but no silent promotion occurs. The policy can enforce review and prerequisite status, not semantic correctness. This is targeted claim review, not an extra monitor agent attached to every specialist.

Test the investigators with unsupported component/field assertions, incorrect but real citations, stale versions, missing prerequisites, summary drift and repeated unproductive searches. Measure unsupported-premise/omission rates, critic detection and escape rates, recovery, abstention and cost. No self-check or critic is claimed to guarantee complete investigation or zero hallucinations. No extra analyst or permanent monitor is added; D2 remains removed.

Local monitors and final review

Both candidates validate schemas, IDs, actual query scope/version, limits and coverage in code for every result. In A, a local task checker reviews specialist work. In D, a shared semantic verifier reviews new claims used to rank causal hypotheses, disputed findings and questionable support; unreviewed claims remain provisional. Each review receives the assigned question, claim and original sources. Return accept, revise, insufficient, or failed with concrete requests. Acceptance does not prove a root cause. Reuse checked evidence only while its source version and scope match.

It can request a specific rival test before causal commitment, for example a historical mapping lookup or provider receipt. Structural separation does not eliminate shared-model bias. Review/rework is bounded and may end with a limited report.

Revisions share task/global budgets; do not retry until a checker agrees. Unavailable sources, agent exceptions and exhausted limits retain partial findings and explicit status. A cross-domain gap becomes a question for D1, which can delegate a targeted follow-up; independent ready tasks may proceed. Checking need not create permanently running extra agents or an infinite hierarchy of monitors. Lifecycle correctness: the three review findings are now explicit

Canonical semantics live in the shared protocol; every individual agent contract inherits them.

  1. Late parallel results: task/result IDs, attempt identity, scope revision and specific dependency versions accompany each result. Ingestion checks authorization, structure, duplicates and applicability before claims change. A changed global case revision alone does not discard independent valid evidence. A late result for old group A stays A-scoped history or needs revalidation; it cannot silently explain current group B. Use version-checked atomic updates, not agent overwrites.
  2. Revocable version-bound approval: D7 review binds the exact report bytes/hash, scope, reviewed claim revisions and evidence/coverage dependency manifest. Material changed/contradicting support, scope or report content invalidates affected approval; unrelated updates need not invalidate everything. A delivery guard atomically verifies current validity. Relevant late evidence after delivery creates a superseding correction record, not silent history edits. Semantic materiality is not perfectly decidable; measure detection and invalidation errors.
  3. Reviewer failure and stopping: a reviewed inconclusive diagnosis is distinct from an incomplete investigation. reviewed_report requires a valid final artifact approval; its diagnosis can be cause_supported, cause_unresolved or complaint_unverified. If review fails, times out or cannot finish within budget and no valid approval remains, return deterministic investigation_incomplete status with stop reason, pending work and clearly unreviewed references—not an approved causal report. This fallback must work even if D1/D8 is unavailable.

All attempts and retries consume shared limits; duplicate result delivery does not double-apply findings or double-count an already recorded attempt. Cancelling a task is best-effort, so late-result policy still applies. Budget reservation for final writing/review is configured but cannot guarantee success. Planned tests include out-of-order results, stale report approval, material versus irrelevant updates, duplicate events and reviewer outage.

Investigation contract

Investigators choose queries, interpret observations, and request follow-ups. Query tools retrieve validated records with provenance and complete/partial/failed status. Each task records its question, tentative scope, rationale, and budget. Shared state keeps raw evidence, revisions, hypotheses, counterevidence, unknowns, and query failures separate.

Delegate questions such as “Was M17 consumed by a worker?” rather than “collect logs.” Each result includes observations, original source references, supported/weakened hypotheses, counterevidence, coverage and any unexpected lead. Preserve source snapshots/references; allow interpretations to become disputed or superseded. Reconsider dependent conclusions and cancel obsolete tasks when supporting findings or scope changes. Multiple summaries of the same source are not independent corroboration.

Do not equate a symptom with a cause, missing evidence with contradiction, repeated summaries with independent observations, or a plausible AI answer with correctness. Rank hypotheses and distinguish initiating faults from contributing failures. Define confidence from evidence and limitations; do not present invented probabilities as calibrated.

The runtime must enforce parallel task dependencies, timeouts, bounded retries, recovery, per-task limits and aggregate budgets. Criticism can trigger another bounded evidence-gathering round. Stop with a valid reviewed report (including inconclusive/unverified-complaint outcomes) or deterministic incomplete status when valid final review is unavailable.

Coverage limits and safe investigation

Domain names are capabilities to demonstrate, not proof that all faults are covered. Explicitly test async queues/dead letters/retries/duplicates/order, stale caches/replicas/indexes, external permission/rate-limit/delivery failures, client visibility, effective network/config behavior, concurrent faults, false alarms and missing/contradictory telemetry. Use the existing specialists rather than adding one permanent agent per technology. Report the supported event/cohort and remaining blast-radius uncertainty separately.

Enforce tenant-scoped, least-privilege, read-only tools, bounded query ranges/row counts/compute, and secret/PII redaction. Retrieved logs/code/documents/prompts are untrusted evidence, never authority to change investigation instructions or permissions. No deployment, database write, customer message send/retry or production experiment is authorized by a diagnosis request. Recommend actions and conditions; safe replay/testing belongs in the simulated evaluation environment. Record the investigators' own tool/agent failures separately from application faults.

Example connecting AI behavior and data

For “the agent gives wrong answers,” determine the affected workflow/runs. Suppose the source record exists and the database tool returns it, but a handoff drops a required field and the next prompt substitutes a default. Evidence supports a coordination defect with a prompt fallback as a contributor. A different run could instead have a missing row, stale retrieval, wrong query filter, or malformed tool response. Test these alternatives; do not blame prompts merely because the output is wrong.

The application's agent traces are evidence under investigation. Our investigation agents' own execution traces are a separate audit trail. Both need stable identifiers; neither provides hidden ground truth to investigators.

The 42% number is top-five culprit retrieval, not top-one diagnostic accuracy, not 42% of arbitrary infrastructure incidents, and not a multi-agent-versus-single-agent win. Lessons to consider later — not architecture decisions

  1. Start from useful evidence contracts. Session/release identifiers and relevant intervals can make a specialist's job far narrower than a raw incident description.
  2. Give each parallel investigator a concrete question and a scoped evidence set. Specialization needs operational meaning beyond changing a role prompt.
  3. Preserve the provenance of evidence through consolidation. A timeline is useful only if each claim can be checked against its source.
  4. Treat model turns, fan-out, tool retries, and validation retries as different budgets. Uber publishes some limits; an assignment implementation must make its own aggregate limits explicit and measured.
  5. Keep domain instructions separate from execution machinery when that separation reduces maintenance. Runtime marketplace infrastructure itself would be disproportionate for a small assignment.
  6. Measure exact RCA correctness separately from partial usefulness and repair acceptance. Each answers a different question.

Exact tool catalog

Status: proposed interfaces, not installed adapters. Generated from definitions.mjs; 41 operations. Seven agent IDs; no D2. Start with where tools execute. All nested types and bounds are defined in tool-contracts.json.

Common calling convention

The model requests a tool name and its JSON arguments. Every input below requires every listed key, including limits; use null only where nullable, and [] for an empty list. Server caps override model limits. An empty filter cannot bypass tenant policy. Source references must come from authorized discovery; no credentials are arguments. All tool returns use the shared receipt below; operation-specific fields belong inside data.

ToolLimits = {max_items: positive integer, timeout_ms: positive integer, max_output_bytes: positive integer, max_scan_bytes: nonnegative integer or null}. Null means use the connector's enforced default cap, not unlimited work.

ToolReceipt = {call_ref, tool, status, data, evidence_refs, coverage, next_cursor, error, cost}. Exact schema: tool-receipt.schema.json. The runtime records the receipt; the LLM does not manufacture it.

StatusMeaning
okRequested operation completed with returned data. Does not imply a diagnosis.
emptyA successful search/read has no matches within recorded scope; data contains typed empty collections. Not global absence.
partialUseful data exists but pages/partitions/ranges/retention or another prerequisite are incomplete.
deniedTrusted policy disallowed the operation; no permission-sensitive data leaks.
not_foundA specific authorized resource/revision could not be resolved. Not an empty general search.
unsupportedThe configured connector lacks this operation/history/revision.
timeout / errorExecution failed; error carries code/message/retryability. No automatic negative finding.

For a hard failure with no usable result, data=null; partial results must still match that tool's data schema. Control operations may return operational status ok while their own data says pending/queued. Source evidence refs may be empty for a control operation.

Coverage records actual scope, query description, source snapshots, source observation/watermark/lag/index freshness, sampling/retention, completeness, pagination and scanned bytes. Unknown values are null, not fabricated. A receipt is provenance of a query, not causal proof. See lifecycle protocol.

Shared types and aliases

Exact nested fields are in the JSON schemas. In particular: SourceLocation = repo + immutable commit + path + line range + evidence refs; EntityKey = field + scalar value + evidence refs; Scope = discovered entity/repository refs, tentative feature terms, nullable environment/time range; ReadContract = code caller + discovered connection/relation/lookup fields + version bindings + evidence + gaps.

Previous conceptual names code.symbol, case.read_review_snapshot, case.read_report_snapshot and ai.list_workflows/runs are not extra endpoints. Use code.search(kind="symbols")/code.references, case.read(view="review"), case.read(view="report") and ai.list_workflows/ai.list_runs. Generic queue/provider/cache/network/DB diagnostics in older notes map to the concrete tools above. No arbitrary shell, SQL or production mutation tool is exposed.
