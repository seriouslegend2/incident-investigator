Three concrete lifecycle examples
  1. Late data: D5 started a group-A query; the complaint is narrowed to group B before it returns. A's result remains A-scoped history, not evidence about B.

Challenge the design: what prevents a confidently wrong answer at scale?
Failure of the investigation itselfRequired response
The true cause is outside the first search page or alerted serviceRetain uninspected candidates and query history; allow alternative-source/neighbor expansion and a critic-triggered rival test. Measure retrieval recall, not only final answer quality.
Code index/catalog is stale or the deployment used several repositoriesTrack freshness and many-to-many artifact/source mappings. Fetch an authorized bounded exact-revision slice if possible; otherwise preserve the missing binding. Never silently use the latest branch.
Millions of duplicate errors hide a rare initiating eventUse backend aggregation plus source-linked representatives, rare-pattern and counterexample retrieval. Preserve counts/time scope; do not equate most frequent error with initiating cause.
One trace is missing, sampled or split across asynchronous workUse message/job IDs, span links and queue records with explicit coverage. Absence of a span does not establish nonexecution or provider health.
A shared dependency has thousands of neighbors or several faults coexistExpand bounded neighborhoods/cohorts, detect cycles and keep multiple causal chains. Report the unexplored frontier instead of claiming exhaustive coverage.
Search is expensive or many incidents run concurrentlyEnforce per-source/tenant concurrency, scan and global budgets outside the LLM; cache only scope/version-safe results, cancel obsolete work and apply backpressure. A small result limit alone does not bound backend cost.
Another tenant's data or malicious retrieved instructions enter the searchAuthorization applies to search, ranking, original fetch and cache. Redact sensitive values; source content is evidence, never permission or instructions. No production writes.
How we would prove scale—without pretending a small demo proves it

Test rising repository/service counts and 10k / 100k / 1m telemetry records with held-out faults, including true causes outside the initial candidates. Record source-retrieval recall, diagnosis/grounding, index freshness, backend bytes scanned, latency percentiles, concurrency and all-model tokens. Measure index/storage/ingestion costs separately. A billion-line claim requires representative real indexing and sustained-load tests; these are planned tests, not completed results. Give the single-agent baseline the same retrieval tools and permissions.

How the system checks its own investigation—not just the application
  • D1 decision record: known premises/source references, exploratory assumptions, unknowns, why this task is needed and what information could change the explanation. Specialists return suggested follow-ups as well as observations.
  • Before dispatch: ordinary code checks valid references, discovered concrete IDs, prerequisites, authorization and limits. Tentative search terms remain search candidates. Reference existence cannot prove semantic support.
  • Review is not only D1's choice: policy requires D7 review when a new architecture/read-contract premise first constrains cross-domain work, a contradiction/prerequisite is flagged, a causal claim is promoted, and before delivery. Related claims can be batched; failed review leaves them unverified.
  • D7 premise/coverage challenge: inspect original sources. Ask “where did this field/component come from?” and “which necessary check is missing?” D7 can request discovery or an alternative test; the policy cannot guarantee its judgment is correct.
  • Repair or stop: downgrade unsupported claims, revisit affected tasks, gather the missing evidence or return a scoped inconclusive report. Do not rely on the user to notice a missing code/history check; do not loop until a reviewer agrees.
  • Test the investigator: inject invented components, irrelevant citations, stale code, missing history, contradictory cohorts and partial-query summaries. Measure detection/escape rates and cost. These are design requirements, not implemented guarantees of zero hallucinations.

So the arrows are investigation results. A catalog or runbook can provide an initial map, but we verify relevant links and revise it. We do not pre-supply the faulty service, require a complete system map, or assume all applications use a queue.

Where “should happen” comes fromFeature contracts, tests/runbooks, service relationships and versioned code/configuration. Code shows the implemented path; it may itself be wrong, so it is not automatically the specification. Every expected step has a source or is labeled an assumption.
Where “did happen” comes fromThat attempt's events, traces, queue state, database history, effective deployment/config and provider receipts. A comparable successful run is useful additional evidence, not required input and not something we invent.

What the architecture review changed—and what we still must test
  • Questions, not collection: specialists investigate claims with local reasoning; they are not passive evidence fetchers. Keep out-of-scope leads so narrow tasks do not hide another cause.
  • Revisable findings: observations retain their source references; interpretations can be disputed or superseded. Reconsider dependent explanations when a finding is overturned. Repeated summaries of one record are not independent evidence.
  • Independent challenge: D7 can inspect original sources and request a rival test before causal commitment and again before delivery. Every review is bounded; approval is not a correctness guarantee.
  • Safety and recovery: scoped read-only tools, privacy/secret redaction, untrusted retrieved content, explicit empty/partial/error/denied outcomes and bounded retries. No automatic production changes.
  • Coverage tests: queues/retries/duplicates, caches/replicas, provider delivery versus UI visibility, permissions/network/config, AI prompt/retrieval/tool/handoff failures, multiple faults, missing telemetry and the investigators' own failures. More boxes do not prove coverage.
  • Measure the benefit: compare the basic supervisor, this improved policy and an equal-tools single agent with at least ten incidents; hold out variants, prevent future-answer leakage, and report accuracy, grounding, calls, latency and all-model tokens. No claim that every incident is diagnosable.

Source-backed mechanisms: focused investigators and independent verification; revisable findings and time-frozen evaluation; targeted hypothesis tests. Execution-path comparison and our exact role contracts are our synthesis, not a claim that these companies implement this exact design.

My recommendation: D, a hypothesis-driven task graph with shared evidence and targeted review. Keep your dynamic delegation and independent final critic. Make the next task an explicit test between possible causes; separate LLM planning from runtime scheduling.

This is a proposed combination of researched patterns, not a deployed product or a demonstrated improvement. A remains a credible simpler implementation; the final choice needs evaluation.

D · NAMED COMPONENTS + STEP-BY-STEP EXAMPLE

Seven agents: D1, D3–D8. Three software components: R1–R3.

D = an LLM agent role. R = ordinary software, not another thinking agent. D2 is removed; its reasoning work belongs to D1. Other IDs stay unchanged. H1–H3 name possible causes; E1–E6 name source evidence.

Who are the seven agents? What does each receive and return?
AgentReceives → does → returns
D1 · Investigation leadVague report and current findings → discovers scope, maintains competing hypotheses, synthesizes evidence, chooses distinguishing tests and delegates bounded work → revised explanation and tasks; delivers the reviewed report.
D3 · ObservabilityA scoped question → searches logs/metrics, compares onset and healthy/affected instances → findings, source IDs, coverage, and next questions.
D4 · Code / change / infraA code/change question → inspects deployed code, rollouts, infrastructure, config/env and version history → a mechanism or finding with versioned evidence and gaps.
D5 · Database / dataA data/dependency question → checks actual records, query semantics, database behavior and dependencies → evidence about missing/wrong data or storage faults.
D6 · AI behaviorA workflow/run question → traces prompts, model settings, retrieval, tool outputs, routing, handoffs and state → where behavior diverged, plus evidence and follow-ups.
D7 · Verifier / criticA claim or exact report plus original evidence → checks support, alternatives, contradictions and limits → accept, revise, insufficient, or a concrete request to D1.
D8 · Report writerReviewed hypotheses, evidence and gaps → writes ranked causes, confidence, counterevidence and actions → a versioned draft for D7; adds no unsupported claims.
R1 · Scheduler / supervisor · CODERuns D1-authorized tasks when prerequisites are ready; enforces parallelism, timeouts, retries and total budgets.
R2 · Investigation board · STOREKeeps original report, tasks, evidence references, hypotheses, review status and revisions. It stores; it does not reason.
R3 · Result validator · CODEChecks result schema, source IDs, query scope/version and coverage; records valid results as provisional or failed, never as automatically proven causes.
D7 appears twice in the diagram because it does two review jobs: claim review during investigation, and independent final-report review. They are separate review calls with fresh context—not two extra agents; D1 does not approve its own reasoning.

    03 · The practical difference

    “The AI answer is wrong.” What question gets asked?

    A · Your design can investigate well

    Call AI / data experts→Monitor each answer→Lead chooses follow-up

    It works if the lead keeps alternatives alive. A local monitor can accept relevant logs even when the overall investigation is following the wrong theory.

    D · Make those alternatives explicit

    H1: data missingH2: retrieval wrongH3: handoff drops data

    First ask whether the source record existed at run time. If yes, inspect retrieval/tool output; if correct, inspect the handoff. These questions distinguish the candidate causes. The actual order changes with available evidence.

    Why this is not “collect everything, then think”: an early result changes the hypothesis board and task priorities immediately. Independent distinguishing checks may run together; dependent checks wait. The investigation can stop without calling every expert.
    04 · My concrete recommendation

    Keep your structure. Change the work-selection and review policy.

    Keep from your design

    • One orchestration owner and specialists exposed as tools.
    • Dynamic selection, retries and explicit follow-up requests.
    • Shared evidence and an independent final critic.

    Add in D

    • Hypotheses with support, contradiction and unanswered questions.
    • Tasks with prerequisites and expected observations that would change the ranking.
    • A runtime that dispatches ready work and enforces the combined budget.

    Change your monitor idea carefully

    Every result: validate schema, evidence IDs, actual query scope/version, errors and coverage in code.
    Before causal promotion: a separate semantic verifier checks new claims used to rank causes, conflicts and questionable support. Unreviewed claims stay provisional.
    Before delivery: review the exact report, source evidence, alternatives and recommendations. No checker guarantees correctness.

    Reuse a checked finding only while its source version and scope still match. Changed evidence can invalidate it and reopen a hypothesis.

    How to choose between A and D without guessing

    Both must meet the assignment and run against a single-agent baseline. Use the same at-least-10 incident suite, model, tools, raw reports, failure replay and documented budgets. Compare root-cause accuracy, grounding, tool-call count, end-to-end latency and all-model tokens. Also record review calls and the effect of local-monitor versus shared-verifier policy. Do not tune to hidden labels.

    If D's bookkeeping and extra planning do not improve diagnosis or grounding enough to justify their cost, choose A. A missing source must yield a gap in either design; a blocked review or exhausted budget can yield an inconclusive report.
