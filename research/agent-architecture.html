Incident Investigator — simple architecture

An operator gives only a vague complaint. The system finds evidence itself. Models never receive the whole repository, database, or log archive.

Reading key: green means implemented and verified locally; the billion-scale index layer remains the production target. The runnable demo uses the same bounded-tool shape against one local repository and simulated Supabase sources.

4. Example: “order confirmation did not arrive”

  1. D1 starts with no evidence. It asks D3: “trace this order's confirmation path”; and D4: “find checkout → email code and deployment path.”
  2. D3 first finds the matching trace/request, then searches its log slice, then checks the narrow delivery/error metric window. It returns only those correlated records.
  3. D4 maps the service path, searches the local clone for sendOrderConfirmation, reads a small source range, and checks the matching deployment/config difference. The checkout service posts to email and uses a one-second deadline. D4 cites path/line snippets; this is not yet a causal claim.
  4. If D4's cited code/deployment contract names a delivery relation, D1 can then ask D5 to describe the allowed projection, look up the exact row, and inspect its short history. Without that contract, D5 is blocked.
  5. D7 checks whether the proposed reason is supported. If evidence conflicts, it sends a narrow follow-up task back to D1. D1 routes it to the needed specialist, then D7 reviews the new evidence again.
  6. D8 writes expected path → observed path → conclusion or “insufficient evidence”. D7 checks the exact wording before delivery.

5. Important boundaries

QuestionAnswer
Does D1 know the whole architecture?No. A bounded index lookup returns a small candidate workflow slice; D4 then proves the relevant code/deploy path with source citations.
Does an agent receive all code/logs as prompt input?No. A bounded tool retrieves small records/snippets; only those enter that agent's context.
Why not just one search tool?Search discovers candidates; it cannot reliably show a trace path, exact source context, a deploy diff, a data history, or an AI handoff. Each specialist therefore gets 3–4 purpose-built reads with strict scope and call limits.
Can D5 change data?No. D5 is read-only. Supabase writes are made by our investigator backend to record cases/evidence/reports.
Can every specialist be called?No. D1 chooses based on complaint/evidence gaps. D7 can request a narrower second task.
Honest status now?Supabase storage, seven agent packages, LangGraph workflow, source-specific bounded tools, OpenAI runtime, prompt publishing, LangSmith tracing, local reference repo, and an email-confirmation live run are ready. The billion-scale ingestion/index layer is still a production build phase.

6. How this works at billion-line / billion-log scale

Agents do not scan repositories or log archives. Connectors continuously build and update narrow indexes. During an incident, agents query those indexes first and fetch raw source only by exact, already-scoped identifiers.

Where Supabase fits: it is our durable investigation ledger and the small demo data source. It is not the place to ingest a production billion-log archive. In production, source-specific backends keep that scale; Supabase stores the case, tasks, citations, findings, report and audit trail.
