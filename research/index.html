01 · First, resolve the ambiguity

The user does not need to identify the incident for us.

The incident input is just free text: “Checkout is acting weird,” “It keeps failing,” or “This worked yesterday.” No affected service, environment, timestamp, error code, request ID, logs, or other evidence is required from the user. A complaint is a lead to investigate, not a verified diagnosis.

User supplies: “Something is wrong with checkout” or “The agent is giving wrong answers.”

System discovers: the observed failure, affected workflow/services or agent runs, scope and timing, and then the likely cause.

Available separately: codebase, database records/diagnostics, telemetry, deployments, settings, AI execution traces, and history. These are searchable sources, not evidence attached to the message.

The PDF requires an incident report and access to queryable sources. Our input contract accepts a vague report. We create the simulated environment, and investigators discover relevant evidence within it.

What about the named agents?

There is a real wording inconsistency: the PDF says “at least five” but lists six roles. It does not call them examples. However, it specifies no exact graph, framework, or one-agent-per-source arrangement. We can design our own coordination and specialization while showing how every listed responsibility is covered.

Source: original assignment, objective and core requirements. Treating the six roles as entirely optional would be an assumption, not something the PDF explicitly permits.

02 · What we have to create and give back

Our scope includes conventional applications and AI applications.

We investigate incorrect behavior as well as crashes or downtime. An AI request can return successfully while its answer is wrong. The following sources are required capabilities for our system; querying every source on every incident is unnecessary:

The PDF's minimum and our product scope differ: codebase, database contents, and AI behavior are explicit requirements established in this discussion. The synchronized Markdown specification is system-requirements.md.

Version and timing matter: inspect deployed code, effective settings, and the prompt/model/context actually used for the failing request. Current repository files, the latest prompt template, or today's database values do not establish what that earlier run saw.

Final submission: runnable code and setup; coordination diagram; at least 10 synthetic incidents with tests; a single-agent baseline using the same tools; comparison on accuracy, evidence grounding, calls, latency, and tokens; a ≤500-word technical note; and the coding-assistant transcript.

Use small versioned repositories and coherent simulated database contents, infrastructure records, and AI run histories. Live production access is unnecessary. Any language/framework/provider is allowed; no polished frontend or automatic production repair is required. Document incomplete features and dependencies. Evaluator answers remain inaccessible to investigators.

04 · A concrete design to discuss

Give AI behavior an explicit investigator. PROPOSAL

The architecture comparison evaluates A: your dynamic supervisor/local-monitor design; B: fixed outer stages; C: peer handoffs; and D: my hypothesis-driven task graph with shared evidence and targeted verification. D is my recommendation to evaluate, not an agreed or proven architecture. The roles below are available capabilities, not a mandatory execution sequence.

The current design has seven agents: D1, D3, D4, D5, D6, D7 and D8, including four domain investigators. D2 is removed; D1 owns reasoning plus orchestration. Existing specialist IDs are preserved. The AI investigator runs when an AI workflow is implicated; AI investigation remains required scope.

Discovery comes before a scoped diagnosis. The Coordinator considers possible meanings of the complaint, asks investigators to map the feature to candidate services and look for matching symptoms, then narrows the work using evidence. This is a first phase of the existing roles, not an assumption that the input already names the failing service.

D1 must earn its specific questions. First locate an observed failing stage; ask a specialist to explain its actual inputs, reads and failure branches; then ask about the discovered fields/dependencies. A cache is not an application fact merely because it is a familiar possibility. Preserve known premises, exploratory assumptions and unknowns separately. D7 also audits unsupported premises and omitted checks in our investigation—not only the application's bug. See how the questions arise, and how the system checks itself →

Expected versus observed: build a provisional workflow from contracts/tests, service relationships and versioned implementation; trace an actual matching attempt and locate verified divergences or unknown boundaries. A comparable successful run helps when available but is not required. Implemented code can itself be wrong, missing telemetry is not proof of nonexecution, and finding a failure point is not yet explaining its cause. See the side-by-side delivery example →

A recent time window can be an initial search assumption, recorded as such and expanded when needed. Keep multiple candidate scopes when the complaint could refer to different workflows. If searches cannot distinguish them, ask a targeted clarification—for example, “Does it fail before payment or after you submit?”—while continuing any useful independent checks. Never invent a specific incident to fit the message.

RoleQuestion it owns and work it performs
D1. Investigation leadWhat could the complaint mean, which causes fit, and what should we check next? Lead discovery, maintain competing hypotheses, combine cross-source findings, choose distinguishing tests, delegate bounded work, and revise the explanation and plan from evidence and criticism.
D3. Observability investigatorCan we observe the reported symptom? Survey candidate workflows, then search logs and metrics to locate failures, onset, affected versus healthy instances, and upstream clues.
D4. Codebase & change investigatorWhich code implements the reported feature, and what behavior could explain the failure? Map the workflow to deployed routes/functions and database calls; investigate deployments, diffs, flags, config, and env changes. Existing code can fail under new load without a recent commit.
D5. Database & dependency investigatorIs source data missing/wrong, or is storage failing? Inspect scoped records and integrity/freshness, transformations, query semantics, schemas, plans, connections, locks, and service/database dependencies. Request calling code or retrieval context when needed.
D6. AI behavior investigatorWhere did the agent's behavior diverge from the intended task? Trace the actual prompt, model output, retrieval, tool calls, routing, handoffs, and state. Compare successful/failing runs; distinguish prompt, context, data, model, tool, and coordination hypotheses.
D7. Independent criticDid we identify the user's actual issue, and what could make the conclusion wrong? Independently audit scope, original evidence, temporal order, alternatives and gaps; request a targeted rival check. Do not become the primary investigator approving its own work.
D8. ReporterWhat did we establish? Explain the observed issue, reviewed cause ranking, uncertainty, actions, and unverified gaps. For AI failures, identify the supported request/step/version and contributing faults.

The brief's reasoning responsibility is merged into D1 along with orchestration; observability, dependency/change, independent criticism and reporting retain explicit owners. This is the user's chosen architecture, not a claim that the PDF explicitly labels its listed roles optional examples. There is no separate analyst agent.

Vague complaint → discover the failing workflow or agent behavior → establish or revise scope → trace application, data, infrastructure, or AI execution evidence → independent review → report.

Feedback: discovery and diagnosis can revisit each other. Investigators share findings and request cross-domain checks. Unknown scope can lead to clarification or an honest unverified result.

Why group code and changes? Application behavior, the deployed revision, and its effective settings often need to be investigated together. This role also reads unchanged code when symptoms point there. Keep separate query tools, and split into independent Codebase and Change agents if evaluation shows that combined scope hurts quality. An environment variable belongs to configuration evidence; it does not automatically need its own agent.

These are investigation owners, not tool-access silos. A database investigator can request deployment context; an observability investigator can follow a dependency. Each chooses queries, interprets results, and requests follow-ups. Run only the relevant branches; do not invoke every source for every incident.

Only after discovering that payments are affected might a task become: inspect the payment module between observed healthy version v41 and failing v42 during 09:55–10:10. Those versions, service names, and times come from discovery tools, not the original message. Scope can change as evidence arrives.

05 · What actual collaboration would look like

From “checkout seems broken” to a traceable explanation.

Invented example to explain the proposal, not a hardcoded test answer.

  1. Only input: “Something is wrong with checkout.” There is no service, time, or evidence attached.
  2. Discover the symptom: catalog/code searches map checkout to candidate frontend, inventory, and payment services. Broad health checks find elevated payment timeouts while other checkout steps look healthy. Targeted queries establish the affected instances and a recent failure window. The payment incident is now an evidence-backed interpretation of the complaint.
  3. Start tracing: tools find a payment deployment at 10:04 and database-related errors. D1 keeps rollout regression and database trouble as candidates; these facts were retrieved, not supplied by the user.
  4. Critic: “Did failures start before that deployment?” The Coordinator asks Observability to extend its time window.
  5. New evidence: matching errors already occur at 10:02 on affected instances. After verifying comparable timestamps and that no canary activated earlier, this argues against the 10:04 rollout as the initiating cause, though it could still worsen the incident.
  6. Dependency follow-up: payment errors point to a database. Its diagnostics show connection rejections. The investigator requests the database's earlier configuration history.
  7. Cross-source explanation: the change investigator finds an effective connection-limit reduction at 10:01. D1 checks whether observed demand exceeds that limit and compares other causes before raising this hypothesis.
  8. Result: report the supported chain and a conditional corrective recommendation. If the configuration query fails, report the observed connection failures and an unresolved cause; do not invent the limit change.

If several checkout problems fit the complaint, the system must retain that ambiguity or request clarification. If it cannot observe a matching problem, report the searches and limits rather than claiming the application is healthy or inventing a root cause. The tools retrieve records; investigators determine both what the issue is and what may have caused it.

AI example: “The agent gives wrong answers.”

Discover the affected workflow and inspect candidate runs. Suppose source data exists and the database tool returns it correctly, but a handoff loses a required field and the next agent's prompt substitutes a default. Trace both the dropped state and fallback instruction: coordination may initiate the failure while the prompt contributes. Alternatively, the row may genuinely be missing or retrieval may have filtered it out. These are competing hypotheses to test, not reasons to label every bad answer a prompt problem. Without the relevant run history, report the causal gap.

06 · Rules that make the proposal precise

Define evidence and failure behavior before choosing a framework.

Each task: a question, currently known or tentative scope, reason for asking, and budget. A discovery task may start without a service, instance, time, or version; it must record its search assumptions and narrow them from results. Each result: findings with source IDs, actual query parameters, timestamps, coverage, uncertainties, and next questions. Queries return complete, partial, or failed status. Validate schemas and references in code; retain raw records behind summaries.

Relationship / availabilityMeaning
SupportsA retrieved observation strengthens a particular explanation.
ContradictsAn observation conflicts with a prediction of that explanation, such as the proposed initiating change occurring after the failure.
Unknown / missingA source is unavailable, incomplete, or unqueried. Missing measurements lower certainty; they are not themselves contradictory evidence.

Store availability separately from hypothesis assessment: one retrieved observation may support one hypothesis and contradict another. A partial or timed-out query describes coverage, not a verdict on a cause.

Shared state: preserve the complaint separately from interpretations, scope, tasks, evidence, findings, hypotheses, and failed queries. Link request/run/step IDs, deployed code and prompt versions, data/context snapshots, and handoff/state revisions. Distinguish traces of the application under investigation from our investigator's own execution traces. Record observable actions and inputs/outputs; private model reasoning is not required. Repeated summaries are not independent evidence; confidence needs an evidence-based rationale.

Execution: enforce tool timeouts, bounded retries, agent limits, and a global time/call/token budget across concurrent branches in code. Check late results against relevant scope/dependency versions before updating claims. Approval binds exact report bytes and evidence/claim versions; material changes invalidate affected approval. If final review cannot complete and no valid approval remains, return deterministic investigation_incomplete status, not an approved causal report. A reviewed inconclusive report is a different outcome. Shared lifecycle protocol.

Evaluation: at least 10 varied incidents must exercise code, deployment/infrastructure, missing/incorrect database data, config, and AI failures: prompt regression, stale/filtered retrieval, malformed tool results, lost handoff state, or coordination loops. Include vague reports, conflicting evidence, missing traces, and tool failures. Measure issue identification, causal accuracy, and grounding. Both approaches get the same raw complaint, source access, clarification rules, and failure replay. Hold the model constant; account for all discovery, retries, calls, latency, and tokens. Keep answers and future fixes hidden. These are coverage requirements, not completed tests.
