A safe way to investigate
vague production incidents.

One system starts with a human complaint, discovers the relevant path across code, deployments, logs, data and AI behavior, then returns a reviewed evidence-backed report. It does not assume the path, dump every source into an LLM, or let agents mutate production.

Agreed implementation direction: build real OpenAI-powered agents in the KookarCore style: one folder per agent with its own prompt seed, Pydantic input/output contracts, restricted tool wrappers, executor/build definition and tests. Persist cases/evidence/runs in Postgres or Supabase, use seeded demo source data for development, and send actual LLM/tool traces to LangSmith.

What is fixed

Three decisions remove the biggest confusion.

1. Logical agents, not seven servers

D1, D3–D8 are role prompts plus restricted tool permissions. One Worker/runtime can run them. The queue gives each task an ID, timeout, retry/DLQ behavior and callback.

2. The model never has direct access

An LLM emits a typed tool request. Backend policy checks it. A private gateway queries the configured real source. The LLM sees only bounded, redacted results and evidence IDs.

3. No D2 returns

D1 does dynamic reasoning and chooses next checks. D7 independently challenges evidence and the exact report. D8 writes only. There is no mandatory all-agent fan-out or “everything to one summariser” step. In the runnable demo, one D1-selected task batch completes before one D7 review; production parallelism requires a durable join.

What the user gives: a vague sentence such as “messages are not reaching customer group A.” What the system discovers: candidate service, deployed code path, data contract, actual execution, configuration and AI behavior where relevant. The input does not secretly contain the logs or table name.
Agreed build contract

What will be implemented — and what will not be faked.

Real agent calls

D1, D3, D4, D5, D6, D7 and D8 are separate agent packages, not labels in one Python file or one giant prompt. Each package exposes a definition/build function, prompt seed, Pydantic request/result models, limited tools and focused tests. The runtime calls an OpenAI model; deterministic fixture “decisions” are not a substitute for those calls.

Real demo sources

Development uses a local OpenTelemetry reference repository for code/deploy evidence and seeded Supabase records for logs, traces, data/history and AI runs. Agents genuinely search those sources through bounded tools. The seed data contains no hidden final diagnosis.

Real operational records

Postgres/Supabase stores cases, task invocations, tool calls, evidence receipts, claims and immutable report revisions. LangSmith records actual LLM/tool execution traces and private versioned code-owned prompts. API keys and database URLs are runtime environment variables only.

Runtime path for the demo: FastAPI creates a case → LangGraph D1 gets a bounded topology packet and chooses the next role → a registry resolves the individual agent folder → OpenAI performs a structured tool-calling turn → source-specific wrappers validate scope and return bounded local/Supabase evidence → result/evidence is persisted → D7 checks claims against the cited records → D8 drafts → D7 checks the exact draft before delivery. D7 follow-ups return through D1 for replanning. Every model/tool run carries case/task metadata and exact prompt ID/version/hash in LangSmith.
Explicit non-goals for the demo: no fake agent conclusion, no all-access shell, no arbitrary SQL, no write to application data, no use of a real AWS/Azure/GCP account merely to pretend it is integrated, and no report delivery when D7 cannot review it. Physical architecture

Where everything actually lives.

An operator-facing, authenticated control plane can use KookarCore + Workers. The high-trust source connections live behind a private gateway with separate identities. This is the key difference from simply giving an all-access agent a terminal.

Control-plane stateLLM / queue executionPrivate policy enforcementConfigured real sources
Why the gateway exists: a Cloudflare-hosted worker is useful for agent execution, but it should not expose a private database or cloud account to the internet. The gateway resolves opaque source IDs to real endpoints and credentials internally. The LLM cannot guess or select a database host, AWS account or secret.
Required bridge decision: either run the role runner inside the private network, or expose only the gateway through a private ingress/Tunnel/Access route. In the second option, require edge service-token authentication and an application-level audience/scope token, plus mTLS where feasible and egress/target allowlists. Test the allowed path and wrong-identity denial. The diagram arrow alone does not create this trust boundary.

How AWS, Azure and GCP fit
Keep one provider-neutral adapter interface. An AWS connector can read registered CloudWatch data, workload/deploy metadata, CI provenance and configuration metadata. Azure and GCP receive equivalent adapters only for registered sources. KookarCore’s current CI points to private Azure ACA; AWS Terraform in the checkout may be legacy or parallel, so an operator must confirm each actual environment. Every adapter uses a separate short-lived workload identity and a resource allowlist.
Agent contracts

What each role receives, calls and returns.

Tasks are scoped dynamically. Roles are stable; a generic “search everywhere” agent is not.

D1 INVESTIGATION LEAD

Input: complaint, scope revision, catalogue leads and compact case/evidence state.

Tools: catalogue/history/evidence lookup; task delegation; clarification.

Output: boundary map, alternatives, discriminating next task and stop decision. It cannot assume code/table/source facts.

D3 OBSERVABILITY

Input: candidate service/boundary/time/correlation IDs.

Tools: bounded logs, metrics, trace, message/provider status and correlation.

Output: observed execution plus searched coverage/gaps; not a source-code or DB causal conclusion.

D4 CODE · DEPLOY · INFRA

Input: expected boundary or source discovery task.

Tools: code search/read/reference, build provenance, deployment/config/infra inspection.

Output: cited implementation/deployment facts and a ReadContract; never direct production data queries.

D5 DATA

Input: cited ReadContract or candidate schema, entity and time.

Tools: replica schema/read/history/lineage/cache diagnostics.

Output: scoped data facts, lag/temporal limits and consistency state; no writes, no guessed relation.

D6 AI BEHAVIOR

Input: known AI workflow/run/correlation or discovered AI boundary.

Tools: actual prompt/model/retrieval/tool/handoff/state traces.

Output: observed AI behavior and evidence gaps; not “the prompt file says X.”

D7 INDEPENDENT CRITIC

Input: exact claims, cited evidence and report/draft hash.

Tools: independent bounded source rechecks.

Output: accept/reject/revise gate, counterevidence and unsupported-premise findings. It does not run a second orchestration tree.

D8 REPORT WRITER

Input: cited claim graph, review requirements and report template.

Tools: cited evidence references and draft storage only.

Output: a concise draft; it cannot investigate new facts or approve itself.

Shared runtime NOT AN EIGHTH AGENT

Input: typed task, immutable case-authorised scope and allowed capability list.

Does: validate structured output, inject trusted scope, enforce tool policy, persist receipts, count budgets and reject stale results.

Guarantee: agent text cannot invent evidence IDs, costs, approval tokens, credentials or report hashes.

Exact task/result JSON, 41 tool definitions and full role examples: contract index, tool catalogue, and individual role documents.

The critical code-to-data handoff

How D5 knows what data to look for.

D5 does not receive a replica and the instruction “find the issue.” D1 first asks D4 to discover the implementation path. D4 returns a cited ReadContract, not a guess:

repo + exact revision + file/range → connection binding → relation / view → lookup keys + predicates → selected fields + transform → failure branches → unknown environment binding

D1 gives D5 this contract, relevant code evidence and the case entity/time. D5 verifies that the authorised replica schema actually matches it, then performs the smallest allowed read. The gateway maps the case’s trusted source scope to this source’s tenant/composite key; D5 cannot select a different tenant in tool arguments.

D1: unknown path→D4: deployed code facts→ReadContract
D7: premise check→D5: replica/schema/history→data evidence
Important: a replica shows current state. A time filter does not make it historical. If the complaint concerns yesterday, D5 needs an actual audit/CDC/history connector or must report that incident-time data is unknown.
Dynamic investigation — example

“Customer group A did not receive the reminder.”

This is not a fixed D1 → every agent → report pipeline. Each result decides the next smallest check.

  1. D1 creates a case and discovers candidate sources. The API first binds the operator-authorised source scope to the case. D1 knows only the complaint, this scope and configured catalogue. It creates an expected boundary map: intent → record → enqueue → consumer → destination resolution → provider accept → callback/delivery → customer-visible.
  2. D3 checks actual execution. In a bounded discovered interval it finds attempt M17 and a destination-resolution error before provider submission. Its receipt says what time, service, IDs and coverage were searched.
  3. D4 finds the deployed resolver. It maps the affected service instance to its deployment/artifact/commit, then reads the resolver file range. It returns RC-17: the lookup relation/fields/keys and an explicit unknown about the environment connection binding.
  4. D7 checks the handoff premise. It verifies RC-17 really refers to the deployed version. If it does not, D1 goes back to deployment/code discovery; D5 is not sent to a guessed table.
  5. D5 verifies the safe data path. Given RC-17, group A and time, it checks allowed replica metadata/schema and reads the bounded fields. It finds that a destination row is absent now but historic data is unavailable.
  6. D1 compares explanations instead of overclaiming. “Queue stalled” is weakened because M17 failed before provider submission. “Destination data missing at incident time” remains unproven until history/audit evidence is found. D1 requests that check or retains the gap.
  7. D8 drafts; D7 approves or blocks exact bytes. The final report says what should have happened, what happened, the supported current inconsistency, what was not observable and the next human action. A changed draft/evidence revision invalidates approval.
Good final conclusion: “The attempt reached destination resolution and failed before provider submission. The deployed resolver uses the cited group-destination lookup. The row is absent on the current replica; incident-time history is not yet available, so deletion-before-attempt is an unresolved alternative.” This is better than declaring a root cause the evidence cannot prove.

Non-negotiable safety properties

Read evidence; do not change the incident.

Must exist

  • Separate identities for API, dedicated incident Worker/queue, gateway, each cloud adapter and each replica.
  • Trusted case scope set at case creation and injected by broker/gateway; tool arguments cannot select another tenant.
  • Read-only transactions/network, parameterised templates, revoked function execution and statement/row/scan/page/time/rate caps.
  • Redaction/minimisation before LLM context; encrypted evidence storage and retention rules.
  • Evidence receipt with source/revision/time/coverage/error class and append-only audit records; add WORM/hash anchoring before claiming tamper resistance.
  • Exact report hash + dependency version checked again at delivery.

Must never exist in this investigator

  • Generic shell, arbitrary URL fetch, arbitrary SQL/RPC/function call or raw secret-value tool.
  • Automatic deploy/rollback/retry/replay/message-send or database mutation.
  • Application service-role, primary/DNS database fallback or a shared broad Worker secret bundle for D5.
  • Unbounded repository, log, trace or conversation dump into LLM context.
  • “No logs found” reworded as “this did not happen.”
  • D7 failure or model output treated as approval.
Tests that prove the design, not just the demo

Test failure paths and unknowns.

Connector tests

Wrong case scope/tenant alias, source, interval, query field, write verb, function/RPC call, primary/DNS fallback, secret field and untrusted log text all fail safely. Receipts record a meaningful state.

Workflow tests

Duplicate work, ambiguous enqueue, callback crash, late work, cancellation, queue redelivery, DLQ and task failure preserve evidence history without stale conclusions.

Diagnosis tests

Use missing rows, stale cache/replica, backlog, provider failure, prompt/retrieval/handoff issue, two faults, ambiguous complaint and telemetry gaps. Measure safe abstention too.

Evaluation rule: compare against one agent with the same tools, sources, permissions and budgets. Measure grounded causal accuracy, boundary localisation, multi-cause coverage, citations/coverage, inappropriate certainty, cost, latency and operator usefulness. Do not claim multiple agents are better before this result exists.
Final implementation readiness review

Do not begin a production connection until every answer is yes.

  • Sources are opaque catalogue entries with owner, retention, freshness and permitted operations.
  • Gateway, not LLM/Worker, holds source credentials; the chosen private bridge works and wrong identities are denied.
  • Code facts bind to actual deployed revision/environment/instance when available.
  • D5 uses network-restricted replica credentials, revoked function execution and a history source with documented completeness.
  • Every tool receipt records trusted scope, time, source version, redaction and completeness.
  • D1 and D7 are distinct; D2 has not returned under a different name.
  • Queue/DLQ/callback/supersession has durable inbox/outbox recovery independent of EDA2 TTLs.
  • D7 reviews exact report bytes and dependencies; incomplete is a valid outcome.
  • Human owners approve data classification, retention, access and report delivery.
  • Holdout tests and same-tool baseline are ready before a superiority claim.
Still needed from the organisation: first pilot service/region, real source owners and access model, approved read replica + history, telemetry/CI/CD/AI trace systems, private gateway network path, security/legal data policy, report audience and incident corpus. Until then, this can be implemented and tested with fixtures, but cannot truthfully diagnose their live production incident.
